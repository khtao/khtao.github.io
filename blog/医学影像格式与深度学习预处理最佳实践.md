# 医学影像格式地图与深度学习预处理最佳实践

> 一句话结论：模型翻车，八成不是网络不够深，而是你把一份「带物理坐标的语义契约」当成了一张能 `imread` 的图片。

## 0. 开篇：四个熟悉的翻车现场

- 把 SVS 导成一张单层 JPEG 去训练，40× 下的细胞核边界全变成插值像素，模型学的是下采样伪影；
- 把 NIfTI 用 OpenCV 按 `H×W` 读进来，第三维和仿射一起消失，左右脑颠倒了还浑然不觉；
- DICOM 转完能打开、能跑、AUC 挺好看，直到换了一家扫描仪直接崩——原来模型记住的是染色批次和层厚；
- 把几百万个 256×256 patch 存成几百万个小文件丢在机械硬盘上，DataLoader 开 8 个 worker，GPU 利用率 5%，硬盘灯比显卡风扇还忙。

前三件事的共同点不是「文件打不开」，而是**文件打开了，语义漂移了**；最后一件则是「格式选对了，但 IO 模式和介质完全拧着来」。格式从来不只是后缀，它同时规定了像素怎么摆、尺度是多少、方向朝哪、元数据归谁管，也决定了磁头要跑多少路。这篇博客把常见医学影像格式摊开讲一遍，再给出训练前真正该做的预处理流水线，最后单开一节讲机械硬盘上的大规模数据集该怎么落地。

## 1. 先站队：你的数据是「大图」还是「体积」

这是整篇文章最重要的一个分叉，走错了后面全错。

| | WSI / 数字病理 | CT / MRI / 放射与神经影像 |
|---|---|---|
| 数学对象 | `X × Y × 通道` 的二维超高分辨率图 | `i × j × k`（+ 时间/梯度）的三维或四维体数据 |
| 核心结构 | 多分辨率金字塔 + 分块 tile | 单个规则数组 + 仿射变换 |
| 尺度单位 | μm/pixel（MPP） | mm / voxel（spacing） |
| 方向信息 | 基本没有解剖方向，重点是层级与色彩 | Image Orientation/Position、qform/sform、space directions |
| 典型读取 | 按视口选层级，只解压相交 tile | 整卷或按切片载入，重采样到统一空间 |
| 训练样本 | 从十亿像素里抽 patch | 整卷 / 2D 切片 / 3D patch |

WSI 的「Z」可能来自 Z-stack 或多层聚焦，但那不是解剖体素；体积数据的每一层切片也不等于金字塔的一层。**把 WSI 当体积，或把每层切片当独立样本，都会让 spacing、窗宽窗位和标签一起错位。** 反过来，把多模态体数据压成一张 RGB 大图喂给视觉模型，只适合做缩略图展示，别拿它做诊断结论。

## 2. 格式地图：按「角色」记，比按后缀记好用

### 2.1 WSI 家族的三类角色

| 角色 | 代表格式 | 关键特征 | 训练时怎么用 |
|---|---|---|---|
| 厂商原始容器 | Aperio `.svs`、Hamamatsu `.ndpi`/`.ndp`、Leica `.scn`、Ventana `.bif`、3DHISTECH `.mrxs`、Hamamatsu `.vms`/`.vmu`、Philips `.isyntax` | 私有布局、多层 IFD、JPEG/JPEG2000 tile、厂商标签带 MPP 与扫描信息 | **只读权威副本**。MRXS、VMS/VMU 是「索引 + 数据目录」的多文件容器，只拷主后缀会得到一个头完整、数据缺失的假文件 |
| 开放 / 标准交换 | OME-TIFF（`.ome.tif`，OME-XML）、OME-NGFF（Zarr 目录，chunked 多尺度）、DICOM WSI（VL Whole Slide Microscopy Image，多帧 + SOP Class/UID） | 可审计的元数据、物理尺寸、通道、色彩；NGFF 适合云原生并行读，DICOM WSI 适合 PACS/VNA | 归档、跨机构交付、多中心数据集统一层 |
| 工程计算缓存 | **fmg**、金字塔 BigTIFF、Zarr、LMDB/tile 目录、WebDataset tar shard / TFRecord | 不为交换设计，只为「喂得快」：前者优化随机区域读，后者优化 HDD 上的顺序流式供给 | 训练时的派生副本，随时可重建；HDD 场景优先顺序 shard |

通用 TIFF/BigTIFF 是个中间地带：能装 >4 GiB、能 tiled、能 LZW/Deflate/JPEG，但**没有强制金字塔、没有统一元数据模型**，不约定清楚就别拿它当标准。

### 2.2 体积与神经影像

| 格式 | 后缀 | 该盯住的元数据 |
|---|---|---|
| DICOM 家族 | `.dcm` / DICOMweb | Patient/Study/Series/Instance、SOP Class、Transfer Syntax、Image Position/Orientation；RT/SEG/SR 各自还有对象语义 |
| NIfTI-1/2 | `.nii`、`.nii.gz` | `pixdim`、`qform`/`sform`、`xyzt_units`、`dim`、datatype；4D 的动态轴别丢 |
| NRRD | `.nrrd`、`(.nhdr + 原始数据)` | `space directions`、`space origin`、kinds、units |
| MetaImage | `.mha`、`.mhd + .raw` | ElementSpacing、Direction、Origin、字节序、压缩 |
| MINC / MGH / MGZ | `.mnc` / `.mgh` / `.mgz` | 方向、空间、历史属性；MGZ 是 gzip 的 FreeSurfer 原生格式，注意 RAS/LPS |
| Analyze 7.5 / PAR/REC | `.hdr+.img` / `.par+.rec` | 遗留格式，方向语义弱，转入 NIfTI 前核对间距与维度顺序 |
| GIFTI / CIFTI | `.gii` | 皮层表面与 grayordinates，不是体素图，别和 NIfTI 直接换像素 |
| BIDS | 目录 + JSON/TSV 侧车 | 不是像素编码，是数据组织规范；sidecar 里存单位、任务、序列参数 |

PET、超声、核医学在临床侧基本是 DICOM，科研侧常转 NIfTI；除了空间几何，还要保住放射性药物、时间、剂量、探头采集这些量测语义。

### 2.3 压缩和元数据不是装饰品

JPEG 是宏块有损，放大后块效应明显；JPEG2000（含 HTJ2K）能按 tile 随机访问、也有无损档，但编解码参数与色彩分量采样会决定互操作性；LZW / Deflate / RLE 多为无损，压缩率有限。DICOM 里压缩是 Transfer Syntax 的一部分，**「解压成功」不等于「DICOM 读对了」**。

WSI 侧最容易被悄悄删掉的是：MPP、物镜、扫描仪、染色批次、ICC/白平衡、label 与 macro 图、注释；体积侧最容易被悄悄改掉的是：spacing、direction、origin、单位、帧顺序。它们不进 loss，却决定模型学到的是不是病理/解剖信号。

### 2.4 插播：fmg 在 WSI 家族里到底算什么

`khtao/fmg` 的自我定位是 *"Fast Memory Graphics is a big image type based on lmdb and can use like OpenSlide"*。读源码 + 实测 0.3.0 之后，可以把它讲得很具体：

- **它不是扫描仪格式，也不是标准**。不链接 OpenSlide C 库，不能打开 `.svs`/`.ndpi`；「use like OpenSlide」说的是接口风格，不是格式兼容。
- **磁盘上是双部件**：`slide.fmg`（一个 JSON 文本索引）+ 同名目录 `slide/level0`、`slide/level1`……每层一个独立 LMDB。JSON 里只有 `level_count`、`level_dimensions`、`dimension`、`level_downsamples`、`mpp`、`ext`、`params`、`patch_size`；tile 的 key 是 `str((x, y, x_max, y_max))`，value 是 `cv2.imencode` 后的字节，默认 `.jpg` + quality 90、256 px tile。迁移必须整体打包，只拷 `.fmg` 是空壳。
- **API 很适合训练**：`fmg.open_slide()` / `fmg.create_slide()`、`read_region()` 返回 `PIL.Image`、`save_from_numpy(pyramid=True, mpp=..., patch_size=256)` 用 `::2` 隔点下采样生成金字塔；`level_count` / `level_dimensions` / `level_downsamples` / `properties` 都在。仓库自带的 `test.py` 就是把它包成 `torch.utils.data.Dataset`，用 `DataLoader(num_workers=4)` 按 512×512 网格抽 patch。
- **但它有明确边界**：无 ICC、无 `associated_images`/标签图/宏图、无 `get_thumbnail`、无格式探测、无标准元数据模型；0.3.0 的 `close()` 会抛 `AttributeError`（`with` 退出也会报错），同一进程写完不关写侧 env 就 `open_slide` 会被 LMDB 拒绝；`cv2.imencode/imdecode` 不做色彩空间转换，BGR 数据读出来会被 PIL 当 RGB；写侧 `map_size` 硬编码 1 TiB，真正卡人的是文件系统是否支持 LMDB 的 mmap。

所以它的正确位置是**第三层：计算侧工作副本**。厂商 WSI 管原始证据，OME-TIFF / OME-NGFF / DICOM WSI 管开放归档与临床身份链，fmg 管「多进程随机读 patch 别把整图塞进内存」。别让它当唯一权威副本。

## 3. 打开工具：按「读」和「写」分开选

| 层次 | 工具 | 定位 |
|---|---|---|
| WSI 只读抽象 | **OpenSlide / openslide-python** | `level_count`、`level_dimensions`、`level_downsamples`、`get_best_level_for_downsample`、`read_region`、`get_thumbnail`、`associated_images`、`color_profile`。**只读**，不负责写标准金字塔 |
| WSI 桌面 / 分析 | QuPath、ImageScope、NDP.view、SlideViewer、CaMicroscope、SlideRunner、OHIF（DICOM WSI） | 浏览、注释、质控、导出；OHIF 走 DICOMweb/PACS |
| 体积查看 | 3D Slicer、ITK-SNAP、Horos、OsiriX、RadiAnt、Weasis、MITK、MRIcroGL、FSLeyes | 3D 交互与诊断；对 RT/SEG/SR/WSI 的支持按版本实测 |
| 编程核心 | pydicom、GDCM、DCMTK、SimpleITK/ITK、nibabel、Bio-Formats | 元数据、传输语法、空间处理、多格式探测 |
| 可写工具链 | libvips/pyvips、tifffile、bioformats2raw + raw2ometiff、ome-zarr、wsidicom | 生成金字塔 TIFF / OME-TIFF / NGFF / DICOM WSI |

一条很实用的原则：**源解析交给最懂源格式的实现，空间与元数据校验交给可审计脚本，目标写入交给明确支持目标规范的实现**。别指望「用 OpenSlide 读出来再另存」解决一切，它是只读的。

## 4. 深度学习预处理：一条主原则，三条管线

### 4.0 主原则：把数据分成三层，且每层都可重建

1. **原始证据层**：厂商 WSI 全目录 / 原始 DICOM Series，只读、带哈希和文件清单；
2. **开放交换层**：OME-TIFF / OME-NGFF / DICOM WSI（病理），合规 DICOM 或带完整 sidecar 的 NIfTI（放射）；
3. **训练缓存层**：fmg、Zarr、tile 目录、LMDB、顺序 shard，**允许随时删掉重建**。

三层不只是逻辑分层，也该是**介质分层**：冷数据（原始层、交换层）适合放机械硬盘做归档与顺序流；热数据（训练缓存层）适合放 SSD / NVMe / tmpfs 承接随机 patch 读。把随机采样压在 HDD 上，再漂亮的格式也救不回来——第 4.4 节专门算这笔账。

每次转换记录：源哈希、软件版本、命令、压缩档位、MPP/spacing、tile 尺寸、目标格式版本、时间。没有 provenance 的预处理流水线，出了问题是没法回溯的。

### 4.1 WSI 病理管线（推荐顺序）

1. **入库校验**：确认多文件容器完整（MRXS/VMS/VMU），记哈希；用 `detect_vendor` 或 Bio-Formats 探测真实格式，别按后缀分发。
2. **读元数据**：`level_dimensions`、`level_downsamples`、`properties` 里的 MPP、ICC/color profile、label/macro。不同厂商的 MPP 键名不一致，拿不到就从 OME-XML 或扫描仪元数据补，**不要凭物镜倍数猜**。
3. **低分辨率做组织分割**：用 `get_thumbnail` 或 `get_best_level_for_downsample` 选低层做组织/背景掩码，把 ROI 坐标乘 downsample 映射回 **level 0 参考系**。OpenSlide 的 `read_region(location, level, size)` 里，`location` 永远是 level 0 坐标，而 `size` 是该 level 下的像素数——这个不对称是经典坑。
4. **按物理尺度定 patch**：先定「一个 patch 覆盖多少 μm」，再换算像素，而不是全数据集硬编码 512×512。多中心数据 MPP 不同，统一物理尺度比统一像素数稳得多。
5. **在 level 0 取图**：目标层尽量固定为 0；若必须用低层，先确认混叠是否可接受。
6. **色彩与质量过滤**：核对 ICC/白平衡；染色归一化或染色增广可以做，但参考图与参数要固定、只在训练集上拟合，别把批次差异当成 augmentation 一通乱抹；过滤模糊、气泡、笔迹、背景占比过高的 patch。
7. **写训练缓存**：把校验过的 RGB numpy 数组按 tile 写入 fmg / Zarr / LMDB；JPEG 是有损的，关键任务优先无损或提高质量并做像素级回读比对。
8. **DataLoader 回读断言**：多进程随机抽一批 patch，与源图同坐标比对；记录打开延迟、峰值内存、通道顺序。

```python
import openslide

slide = openslide.OpenSlide('slide.svs')
# 不同厂商 MPP 键名可能不同，先在 properties 里核对，拿不到就从 OME-XML / 扫描元数据补
mpp = slide.properties.get('openslide.mpp-x')
if mpp is None:
    raise ValueError('MPP 缺失：请从 OME-XML / 扫描元数据补齐，不要凭物镜倍数猜')
mpp = float(mpp)

target_um = 256                       # 一个 patch 覆盖 256 μm，而非硬编码 512 px
patch_px = int(round(target_um / mpp))
level = 0                             # 训练 patch 尽量固定在全分辨率层

# 注意：location 是 level 0 参考系坐标；size 是该 level 下的像素尺寸
patch = slide.read_region((x0_level0, y0_level0), level, (patch_px, patch_px))
patch = patch.convert('RGB')          # OpenSlide 返回 RGBA
```

写 fmg 缓存（0.3.0 实测可用写法）：

```python
import fmg, cv2

# rgb: (H, W, 3) uint8，来自 OpenSlide / pyvips / tifffile 的解码结果
w = fmg.create_slide('cache.fmg')
w.save_from_numpy(rgb, ext='.jpg',
                  params=[cv2.IMWRITE_JPEG_QUALITY, 95],
                  pyramid=True, mpp=mpp, patch_size=256)
for env in w._data:      # 0.3.0 必须手动关写侧环境，否则同进程 open_slide 会被 LMDB 拒绝
    env.close()

s = fmg.open_slide('cache.fmg')
print(s.dimensions, s.level_count, s.level_dimensions, s.properties)
img = s.read_region((1000, 2000), 0, (512, 512))   # -> PIL.Image；别越出该层尺寸，0.3.0 边界处理有限
# 别用 with：0.3.0 的 close() 会抛 AttributeError；生产环境请自行封装一层
```

**WSI 管线坑清单**：层级采样错位；`read_region` 坐标参考系；低层 ROI 映射回 level 0 时忘记乘 downsample；JPEG 反复重编码；BGR/RGB 被 `cv2` 悄悄换掉；label/macro/注释在导出时丢失；多文件容器只拷主文件；把不同扫描仪的染色差异当噪声却不做记录；fmg 的 `read_region` 在 0.3.0 里未按 `level_downsamples` 换算坐标，跨层取图前必须实测。

### 4.2 CT / MRI 体积管线（推荐顺序）

1. **DICOM → NIfTI 用 `dcm2niix`**，别自己按文件名排序堆数组；核对自动切分是否按 Series/ProtocolName 合理，dMRI 的 bvec/bval、fMRI/PET 的时间轴与 TR 必须跟着走。
2. **读头校验**：shape、datatype、spacing、origin、direction、单位、qform/sform、动态维度。能读出同一个数组，不代表两个工具的空间约定一致。
3. **方向统一**：先把 RAS/LPS、Image Orientation/Position 对齐，再做任何裁剪或配准；顺序反了会出现「图像看着正常、标签整体镜像」。
4. **重采样到统一 spacing**：各向异性层厚是多中心数据的头号域偏移来源。用 ITK/SimpleITK 保留 origin 与 direction，**图像用线性插值、分割标签必须用最近邻**。
5. **强度处理按模态分开**：CT 有物理单位，按任务协议固定窗宽窗位或 HU 裁剪范围再归一化；MRI 没有绝对强度单位，用百分位裁剪 / z-score / 逐例归一化，**统计量只在训练集上拟合**，别把验证集分布泄漏进预处理。把策略写进配置，和模型权重一起版本化。
6. **空间增强要同步**：任何旋转、缩放、形变都同时作用于图像与 mask，并保持 spacing / affine 一致；4D 数据的动态轴别被当成通道丢掉。
7. **产出与组织**：保存时保留仿射（NIfTI/NRRD/MHA 都行），用 BIDS 目录 + JSON sidecar 管理，`bids-validator` 查结构但不保证内容正确。

```python
import nibabel as nib
img = nib.load('src.nii.gz')
hdr = img.header
print('shape', img.shape, 'dtype', img.get_data_dtype())
print('zooms', hdr.get_zooms(), 'units', hdr.get_xyzt_units())
print('qform', img.get_qform(), 'sform', img.get_sform(), 'sform_code', hdr['sform_code'])
```

```python
import SimpleITK as sitk

def resample_isotropic(img, out_spacing=1.0, is_label=False):
    size = img.GetSize(); sp = img.GetSpacing()
    out_size = [int(round(s * p / out_spacing)) for s, p in zip(size, sp)]
    interp = sitk.sitkNearestNeighbor if is_label else sitk.sitkLinear
    return sitk.Resample(img, out_size, sitk.Transform(), interp,
                         img.GetOrigin(), (out_spacing,) * 3,
                         img.GetDirection(), 0.0, img.GetPixelID())

img = sitk.ReadImage('t1.nii.gz')
print(img.GetSize(), img.GetSpacing(), img.GetOrigin(), img.GetDirection())
img_iso = resample_isotropic(img, 1.0)
mask_iso = resample_isotropic(sitk.ReadImage('mask.nii.gz'), 1.0, is_label=True)
sitk.WriteImage(img_iso, 't1_1mm.nii.gz')
```

**体积管线坑清单**：直接抽 DICOM 像素而不重建 Image Position/Orientation；把 4D 当 3D；重采样时 mask 用了线性插值；不同工具 qform/sform 优先级不一致；Analyze/PAR/REC 的方向与字节序遗留问题；FreeSurfer RAS/LPS 与 NIfTI 混用；归一化统计量跨数据集拟合；BIDS 只过了结构校验却没管内容。

### 4.3 转换场景速查

| 场景 | 工具 / 命令 | 必须校验的点 |
|---|---|---|
| DICOM 系列 → NIfTI | `dcm2niix -o out -f %p_%s in/` | 切分逻辑、bvec/bval、时间轴、TR |
| DICOM 匿名化 | `gdcmanon` / DCMTK `dcmodify` / pydicom 脚本 | 嵌套 SQ、私有标签、UID 重生成、像素内 burn-in 文字 |
| 体积格式互转 | SimpleITK / ITK、Convert3D (c3d)、`mri_convert` | spacing、direction、单位、是否意外触发重采样 |
| 厂商 WSI → OME-TIFF | `bioformats2raw` + `raw2ometiff`、QuPath、pyvips | MPP、tile、BigTIFF、OME-XML、label/macro |
| 厂商 WSI → 金字塔 TIFF | `vips tiffsave in.tif out.tif --tile --pyramid --compression jpeg --Q 90 --tile-width 256 --tile-height 256` | 有损质量、压缩兼容性、MPP 保留 |
| WSI → DICOM WSI | `wsidicom` / 合规 DICOM 库 | 新 UID、帧关系、MPP、ICC、label/overview |
| 大图 → fmg 缓存 | `create_slide` + `save_from_numpy` | 双部件整体迁移、mmap 支持、JPEG 有损、同进程环境 |
| 数据组织 | `bids-validator` + sidecar | 结构合规 ≠ 内容/隐私合规 |
| 大规模数据集 → HDD 顺序供给 | 预切 patch → WebDataset tar shard / TFRecord / 大二进制 + offset 索引 | shard 100 MB–1 GB、单 chunk ≥ 1 MB、训练期只读顺序流 |

### 4.4 机械硬盘上的大规模数据集：转成什么格式、优劣与最佳实践

前面聊的都是「语义不能丢」，这一节换个视角：**当训练数据大到只能放在机械硬盘（HDD）上时，格式选型的第一约束不是元数据丰不丰富，而是磁头要不要移动。**

#### 4.4.1 先算一笔物理账

一块典型 7200 RPM 机械盘：平均寻道加旋转延迟约 **8–12 ms**，随机小 IO 大约只有**百次/秒量级**；但顺序吞吐能到 **100–200 MB/s**。也就是说，一次寻道花掉的 10 ms，够它顺序读 **1–2 MB** 数据。

把这个数字套到 WSI 训练上就很刺眼：一个 `256×256×3` 的 uint8 patch 约 192 KB，JPEG 压完常常只剩几十 KB。如果每个 patch 独立随机读一次，固定成本全付在寻道上，有效吞吐掉到顺序读的十分之一甚至更低，GPU 只能干等。**注意一个反直觉的点：在随机小读的场景里，压缩让文件更小并不会让它更快，因为瓶颈是「次数」不是「字节」；只有把读改成连续大块，压缩省下的字节才真正变成吞吐。**（以上为典型量级，具体盘以 `fio` 实测为准。）

于是结论不是「换一个更快的格式」，而是**换一种 IO 模式**。

#### 4.4.2 结论：转成「顺序打包容器 + 常驻内存索引」

HDD 上该把数据转成 **大文件顺序容器**：WebDataset tar shard、TFRecord / RecordIO、自定义大二进制 + offset 表、把 chunk 调大的 HDF5、启用 sharding 的 Zarr、或按空间顺序写 key 的 LMDB / fmg。共同特征是：

- 数据按**训练顺序**顺序追加写入，磁盘上只留少量大文件；
- offset / length / label / MPP / spacing 等索引**常驻内存**；
- 训练时对 HDD **只读、顺序流**，随机性交给 shard 级 shuffle + 内存 shuffle buffer，而不是交给磁盘 seek。

一句话：**用「顺序读 + 内存里再打乱」代替「磁盘上随机抽样」。** 这几乎是 HDD 上唯一能稳定吃到标称吞吐的写法。至于「随机访问某个样本」，那是 SSD 的职责，不该在 HDD 上硬扛。

#### 4.4.3 候选格式在 HDD 上的优势与缺点

| 目标格式 | 优势（HDD 视角） | 缺点 / 陷阱 |
|---|---|---|
| **WebDataset（tar shard，100 MB–1 GB）** | 纯顺序流、文件数少，吞吐能吃满；天然支持流式读取、分片到多盘/网络、内存 shuffle buffer；样本自带 key 便于溯源 | 不能原位随机取某一条；shuffle 质量依赖 buffer 大小；索引与校验和要自己管；必须离线预切 patch 并固化 epoch 顺序 |
| **TFRecord / RecordIO / 大二进制 + offset 表** | 顺序追加写、零元数据风暴、读放大最小；索引进 RAM 后读路径极短 | 无内建压缩与元数据模型、跨语言弱；追加数据通常要重建 shard；索引文件丢了大库难恢复，必须单独备份 |
| **LMDB（含 fmg）** | mmap + B+tree、零拷贝、ACID、多进程只读并发友好；省掉「每样本一次 open/stat/close」的文件系统开销 | **省不掉寻道**：随机 key 查找仍要若干次 4 KB 页读取，单个 patch 的 IO 等待容易落在几十毫秒量级；单写者；`map_size` / mmap 依赖文件系统；同进程环境占用；fmg 0.3.0 还有 `close()` 缺陷 |
| **HDF5（chunk ≥ 1–4 MB）** | 单文件、内建压缩、按 chunk 局部读、生态成熟 | 小 chunk 直接退化成随机 IO；并发读有锁，多进程需各自打开文件或用 SWMR；单文件损坏会波及整库 |
| **Zarr / OME-NGFF** | 标准化多尺度元数据、并行与云原生友好 | **默认每 chunk 一个文件**，成千上万小文件落 HDD = inode/dentry 查找 + 寻道双重灾难；必须调大 chunk、启用 Zarr v3 sharding 或改用打包 store |
| **Tiled OME-TIFF / 金字塔 BigTIFF** | 单文件 tiled，相邻 tile 可近似连续读，金字塔与 OME-XML 都在 | IFD 链跳转、>4 GiB 的 BigTIFF 边界、JPEG2000 解码的 CPU 开销；写后难改 |
| **原始厂商 WSI / 一 patch 一文件** | 改起来最省事 | **最不该放 HDD**：MRXS / VMS/VMU 本就是多文件目录，每次 `read_region` 都要寻道；百万小文件的元数据开销比数据本身还贵 |

取舍很清楚：**要标准与可交换，用 OME-TIFF / NGFF / DICOM WSI 做归档；要 HDD 上喂得快，用顺序 shard 做训练副本；LMDB / fmg 是「少文件 + 可随机读」的折中，不是 HDD 上的加速银弹。**

#### 4.4.4 fmg 放在 HDD 上，具体会怎样

这一条值得单独说，因为 fmg 恰好踩在两种 IO 模式之间。

好消息来自源码：`save_from_numpy` 写 tile 是 `for x ... for y ...`（x 外层、y 内层），`read_region` 拼一个矩形区域时也是 `for w(x) ... for h(y) ...`，**遍历顺序一致**；一个 512×512 区域只需取 2×2 个 256 tile，比「一个 patch 一个文件」少太多文件级开销。加上 LMDB 把所有 tile 收进少数几个数据库文件，HDD 上至少不用面对百万小文件。

但要泼三盆冷水：

1. **LMDB 的 key 是 `str((x, y, x_max, y_max))` 的字符串字典序**，数字没补零时 `1000` 会排在 `101` 前面，空间相邻的 tile 并不保证物理相邻，连续写入不等于连续读出；
2. 默认 256 px JPEG tile 只有几十 KB，远低于 1 MB 这个性价比拐点，随机跨区域采样仍是纯寻道；
3. mmap 的缺页在 HDD 上就是实打实的磁头移动，`read_region` 又不按 `level_downsamples` 换算坐标，跨层取图更容易跳。

所以 HDD 上用 fmg 的正确姿势是：**把 `patch_size` 调大（512 或 1024，让单 tile 接近或超过 1 MB）、只编码一次、按 x 顺序生成、采样时尽量空间邻近而不是全图乱跳、预热 page cache、`.fmg` 与 `levelN/` 放同一块盘**；更彻底的做法是再包一层顺序 shard，把 fmg 当作离线解码器而不是在线随机读引擎。

#### 4.4.5 最佳实践：可照着做的九步

1. **先定介质分工**：HDD = 原始层 + 交换层（冷、顺序读写）；SSD / NVMe / tmpfs = 训练缓存层（热、随机 patch 读）。预算只够 HDD 时，第 2–9 步一步都不能省。
2. **离线「预切 + 重排」**：把 epoch 的采样顺序（含 shuffle 结果）固化下来，按这个顺序把 patch 顺序写进 shard。**训练时不在 HDD 上做 seek 采样**，随机性交给 shard 级 shuffle 与几百到几千样本的内存 buffer。这是收益最大的一步。
3. **定尺寸**：单 shard 100 MB–1 GB，单样本 / 单 chunk ≥ 1 MB（按压缩前尺寸估）；文件总数控制在几百量级，别造百万小文件。Zarr 用户尤其要调大 chunk 并启用 sharding。
4. **索引常驻内存**：offset/length、key→offset、label、MPP/spacing、样本 ID、患者/切片映射全部读进 RAM；HDD 上只留只读大文件。索引单独存一份带校验和的备份，和数据分开。
5. **单写者离线构建，训练期只读**：HDD 只有一个磁头组，读写混合会互相抢寻道；LMDB 本身也只允许一个写事务。新增数据 = 新写一个 shard，绝不原地追加或改写。
6. **压缩策略分场景**：顺序大 shard 上「CPU 换 IO」通常划算（LZ4 / Zstd 快速档 / 单次高质量 JPEG），少读字节就是少等磁盘；但保证每个块可独立解码、别反复重编码，JPEG2000 这类重解码要评估 CPU 会不会反客为主。随机小读场景下压缩帮不上忙，别指望它救命。
7. **并发按 shard 切，不按样本切**：让每个 worker 独占一个 shard 做顺序流（分片数 ≥ worker 数），`num_workers` 收敛到 2–4 并加大 `prefetch_factor`；**8 个 worker 在同一文件里随机跳，只会让 HDD 更慢**，这和 SSD 上的调参经验正好相反。
8. **物理布局与预热**：数据集、日志、checkpoint 分盘或错峰写；训练前顺序扫一遍预热 OS page cache；用 `iostat` 看 `%util` 与 await，而不是只盯 GPU 利用率。
9. **验收看 IO 指标**：顺序吞吐 MB/s、每个 patch 的平均寻道次数、DataLoader 等待占比、GPU 利用率、缓存命中率；再随机抽一批 patch 与源图做像素级回读比对，核对 shard 校验和与索引一致性。

离线构建顺序 shard 的最小示意（省略压缩、校验和与多 shard 调度）：

```python
import json

# 离线：按「训练顺序」顺序追加写，全程零 seek
def build_shard(shard_path, samples_in_epoch_order):
    index = []
    with open(shard_path, 'wb') as f:
        for sample_id, patch, label in samples_in_epoch_order:   # patch: (H, W, 3) uint8
            buf = patch.tobytes()
            index.append({'id': sample_id, 'offset': f.tell(),
                          'length': len(buf), 'shape': list(patch.shape),
                          'label': label})
            f.write(buf)
    # 索引单独备份：丢了它，整个 shard 只是字节流
    with open(shard_path + '.idx.json', 'w') as g:
        json.dump(index, g)

# 训练侧：一个 worker 独占一个 shard，顺序读 + 内存 shuffle buffer
# 关键：不要在 __getitem__ 里对 HDD 做随机 seek，也不要多 worker 抢同一文件
```

#### 4.4.6 反模式清单

一 patch 一文件；Zarr 默认小 chunk 直接落 HDD；在 HDD 上多 worker 随机 `read_region`；训练时往 LMDB 追加写；把 SSD 上的 worker/prefetch 参数照搬；只看「格式是否标准」不看 IO 模式；以及最隐蔽的一条——**把压缩率当成性能指标，却没测过每个样本平均要付几次寻道**。

## 5. 脱敏、合规与可复现

**脱敏不等于匿名化。** pydicom / gdcmanon / DCMTK 能改显式标签，但 SR 文本里的姓名、私有厂商字段、非标准序列、MAC/数字签名、derived series 的来源追溯，以及烧录进像素的抬头，都不会自动消失。转出来的 NIfTI/OME-TIFF 也可能在 JSON、description、OME 描述里带着 PHI。正确顺序是：最小权限读源 → 策略化删除/替换 → UID 重生成 → 校验 → 加密与访问控制 → 审计。临床数据进训练集的每一步都要能回答「这份数据从哪来、改过什么、谁批准的」。

## 6. 训练前 checklist（可以直接抄进项目 README）

**通用**
- [ ] 原始层、交换层、缓存层三者分离，缓存可一键重建
- [ ] 每次转换有源哈希、软件版本、命令、参数、时间的 provenance
- [ ] 随机抽样做像素级回读比对，而不是只目视看一眼

**WSI**
- [ ] 源/目标文件清单与哈希、全分辨率尺寸、各层尺寸比例、tile 尺寸
- [ ] MPP、色彩空间/ICC、label/overview、OME-XML 或 DICOM 对象字段
- [ ] patch 按物理尺度换算，坐标统一在 level 0 参考系
- [ ] 压缩档位与 BGR/RGB 顺序已验证，JPEG 有损已评估

**体积**
- [ ] shape、dtype、spacing、origin、direction、单位、动态/向量维度
- [ ] qform/sform、NRRD/MHA 头、MGH/MGZ 坐标约定
- [ ] 图像与 mask 用不同插值，affine 与 spacing 全程一致
- [ ] 强度统计量只在训练集拟合

**DICOM / 合规**
- [ ] SOP Class、Transfer Syntax、UID 策略、嵌套序列
- [ ] 匿名化策略与像素 burn-in 检查
- [ ] 打开延迟、峰值内存、并发只读、异常退出后的锁清理

**HDD / 大规模训练缓存**
- [ ] 介质分层：HDD 放冷层与顺序流，SSD / NVMe / tmpfs 放热缓存
- [ ] 按 epoch 顺序预切成大 shard（100 MB–1 GB），单 chunk ≥ 1 MB，文件数控制在几百量级
- [ ] 索引常驻内存并单独备份；训练期对 HDD 只读、顺序读，单写者离线构建
- [ ] worker 按 shard 独占顺序流，worker 数受 HDD 单磁头约束
- [ ] 用吞吐 / 寻道次数 / DataLoader 等待占比 / GPU 利用率验收，而非只看格式名
- [ ] shard 校验和、索引一致性、缓存可一键重建

只有这些断言都通过，才配叫「一次转换是无损且语义保持的」。

## 7. 结语

格式不是后缀，是一份关于像素、尺度、方向和身份的契约。厂商 WSI 负责原始证据，OME-TIFF / OME-NGFF / DICOM WSI 负责开放归档与临床互操作，NIfTI / NRRD / MHA 负责可计算的空间数组，fmg 这类 LMDB 容器负责让 DataLoader 别等磁盘——**没有任何单一格式该同时承担原始证据、开放存档、快速缓存、分析数组和诊断交付**。

再往下一层是介质：SSD 上比的是随机 IOPS，HDD 上比的是磁头少跑多少路。大规模数据集落到机械盘时，与其纠结哪个容器更「高级」，不如把它改成大顺序 shard + 内存索引，让训练变成一条平稳的流。把三层分开、把校验写进流水线、把 MPP / spacing 和寻道次数都当成一等公民，模型才有可能学到组织与解剖，而不是扫描仪的脾气和硬盘的转速。
